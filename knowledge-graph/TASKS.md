6. **Real-device testing found and fixed the actual root cause of backlog item 17 ("every TCP connect() times out") — first time TCP relay has ever worked end-to-end in this project.** Installed Warden on the booted v0 device, started the network monitor, and reproduced the timeout immediately against a real listener. The existing `protect()`-result diagnostic log (committed but unpushed since session 6) showed `protect() returned false` for every single TCP socket. Root cause: `TcpRelayManager.connectAndRelay()` calls `protect(session.socket)` on a bare `Socket()` *before* `connect()` — but a plain `java.net.Socket` doesn't allocate its underlying native file descriptor until `bind()` or `connect()` is called, so `protect()` had no real fd to act on and silently failed; the unprotected socket's SYN then looped back into Warden's own tun interface instead of reaching the real network. UDP never hit this because `DatagramSocket()` allocates its fd immediately at construction. Fixed with one line: `session.socket.bind(InetSocketAddress(0))` before `protect()`. Verified for real: `protect() returned true`, a real bidirectional exchange with a listener on the container's host bridge (`192.168.97.1`), and the audit trail logging it `Safe`. Shipped directly to `main` (no branch — see item 8).

## Resolved — AVF compile blocker (session 2, carried from previous day)

**Root cause, confirmed via `javap` against the real jar, not guessed:** `android.system.virtualmachine.*` (`VirtualMachine`, `VirtualMachineManager`, `VirtualMachineConfig`) are `@SystemApi`, absent from the public `compileSdk` jar. Google's own reference app (`MicrodroidDemoApp`, from `platform/packages/modules/Virtualization`) builds against them via Soong's `sdk_version: "system_current"`, which — inside a full AOSP tree — resolves to `prebuilts/sdk/<api>/system/android.jar`.

**Fix applied (no AOSP checkout needed):** `platform/prebuilts/sdk` is its own standalone AOSP git repo, independently cloneable. `trigger-router/build.gradle.kts` has a `fetchAvfSystemStub` Gradle task that downloads `35/system/android.jar` from `android.googlesource.com/platform/prebuilts/sdk` at build time (cached under `build/avf-stubs/`, not committed — it's a multi-MB AOSP binary) and wires it in as `compileOnly`. Verified locally via `javap` before writing any code that the jar actually contains `android/system/virtualmachine/*.class` with the expected method signatures.

**While verifying the method signatures, found the API shape had actually changed from what the code (and Google's `writeavfapp` doc, which reads as written for an older API level) assumed:**
- `VirtualMachineConfig.Builder` has **no `(Context, path)` constructor** in API 35 — only `Builder(Context)`. Fixed to build the config programmatically: `.setPayloadBinaryName("libnoxos_payload_stub.so")` + `.setProtectedVm(false)`.
- Builder method is `setProtectedVm(boolean)`, not `setProtected(boolean)`.
- `VirtualMachineManager` has no public constructor or `getInstance()` static — obtained via `context.getSystemService(VirtualMachineManager::class.java)`. Agy's original code already had this right.
- `vm.connectVsock(long)` takes a `Long`; `VmPayloadProtocol.VSOCK_PORT` was an untyped `Int` literal (`5000`) — changed to `5000L`.

**Open question this surfaces, still not resolved:** if the host-side `VirtualMachineConfig` Builder no longer parses `assets/vm_config.json` directly (API 35 removed that constructor), it's unclear what role that JSON file still plays — whether Microdroid still reads it by convention on the guest side, or whether it's now fully redundant with `.setPayloadBinaryName()`/`.setApkPath()`. **Did not touch `app/src/main/assets/vm_config.json`** — needs verification against real Microdroid boot behavior (Phase 2), not a guess.

14. ~~**Real TCP relay for `NetMonitorService`**~~ — **done 2026-08-17.** Considered lwIP/tun2socks/NetGuard-native-style first, but all of those are C and `noxos-app` has no NDK/CMake toolchain — adding one just for this would be a new build system, not a fix. Instead hand-rolled a minimal split-relay in pure Kotlin, same shape as the existing UDP relay: new `TcpRelayManager` parses each TCP segment off the tun fd, keys a session table by the 4-tuple, and on SYN opens a real `protect()`'d `Socket` to the destination. Once connected it synthesizes a SYN-ACK back into the tun (the app's TCP stack has no idea it's talking to a relay), then a background coroutine pumps `Socket` input straight into synthesized data/FIN segments, while inbound data/FIN/RST packets get their payload written to the real socket and ACKed. Sequence/ack numbers are tracked per-session as unsigned 32-bit (`Long`, masked); `PacketUtils` gained `readUInt`/`writeUInt` and a real `buildTcpPacket` (pseudo-header checksum included). **Known, deliberate simplifications** (not bugs): no retransmission/window-scaling/reordering — relies on the real destination's own TCP for reliability and on the tun fd (a local kernel path, not a lossy network) rarely dropping; no TCP options echoed on our synthesized segments. Verified with a real JVM integration test (`TcpRelayManagerTest`, no Android/Robolectric needed) that drives a full SYN → data → reply → FIN cycle against a real loopback `ServerSocket` and asserts on the actual bytes relayed each direction — not a stub. Still unverified against a real device/Cuttlefish (same Phase 2 caveat as the rest of the AVF/VM code), but this closes the "TCP traffic invisible to the monitor" gap that the earlier "scan failed" / "select and scan doesn't work" reports may have been adjacent to.
