## Session 22 (2026-09-14/15) — real platform-key signing for release APKs

Backlog item 12 ("real signing infra") was closed as *not our problem, app ships inside the OS image* since session 12 — this session reopens and actually resolves it, because `v0.0.1`'s original signing fix (session 12: point `signingConfig` at AGP's auto-generated debug keystore) had a real, live consequence being felt every release: the debug keystore isn't persisted between CI runs, so it's a **different** key every single time, and every release APK fails `adb install -r` over the previous one (`INSTALL_FAILED_UPDATE_INCOMPATIBLE`) until the old one is uninstalled first — flagged as a "rough edge" in session 10's own entry and never actually fixed until now.

1. **`noxos-os` generated the real platform key and published it as two `noxos-app` repo secrets**: `NOXOS_PLATFORM_KEYSTORE_B64` (base64 PKCS12 keystore, alias `platform`) and `NOXOS_PLATFORM_KEYSTORE_PASSWORD`. **Verified via the actual API before touching anything** (`gh api repos/.../actions/secrets`, not just `gh secret list`'s pretty-printed output) — the first check came back genuinely empty (`total_count: 0`), work correctly stopped there rather than proceeding on the stated premise, and the secrets showed up for real about 19 hours later once `noxos-os` actually finished generating and publishing them.
2. **`release.yml`**: new step decodes `NOXOS_PLATFORM_KEYSTORE_B64` straight to `$RUNNER_TEMP/platform.jks` (piped through `base64 -d`, never echoed to stdout — GitHub also auto-masks the secret value in logs regardless, but this avoids relying on that alone) before `assembleRelease`, and passes `NOXOS_KEYSTORE_PATH`/`NOXOS_KEYSTORE_PASSWORD` as env vars to the Gradle invocation.
3. **`app/build.gradle.kts`**: new `signingConfigs.create("release")` reads `NOXOS_KEYSTORE_PATH`/`NOXOS_KEYSTORE_PASSWORD` from the environment, alias `platform`. **One deliberate deviation from the originally-specced fallback**: rather than falling back to a literal `$rootDir/debug.keystore` path (no such file exists anywhere in this repo, so that fallback would have made local `assembleRelease` builds fail outright for any contributor without the secret — the opposite of the stated goal), `buildTypes.release.signingConfig` picks between the new `"release"` config and AGP's own built-in `"debug"` signingConfig (auto-managed, zero setup, always present) based on whether `NOXOS_KEYSTORE_PATH` is set — genuinely achieves "only CI needs the real key, a contributor without the secret can still build locally" using the mechanism that was already working for exactly that purpose before this change.
4. **Verified for real, not just "build succeeded"**: cut two throwaway releases (`v2.2.1`, `v2.2.2`, no functional changes — pure version bumps to get two independent CI-signed artifacts) after the fix landed, downloaded both release APKs, and ran `apksigner verify --print-certs` (build-tools installed locally for this specifically — this environment had never had more than `platform-tools` before) on both: **identical signer** — `CN=NoxOS Platform, OU=NoxOS, O=NoxOS, C=US`, SHA-256 `950e2918ebbdcdb78faeaed28495dd68b1e97ba59c093031cb74ed0000703861` — on both, and `apksigner verify --verbose` confirms a real `Verifies` pass using APK Signature Scheme v2 (v1/JAR signing is off, which is why `keytool -printcert -jarfile` alone said "Not a signed jar file" on a first, wrong-tool attempt — expected for a v2-only signed APK, not a bug). This is the actual fix for the `INSTALL_FAILED_UPDATE_INCOMPATIBLE` rough edge — confirmed at the certificate level, not inferred from "the workflow went green."
5. **Signing-infra note**: this closes backlog item 12 for the release-APK-signing half of "real signing infra" — no change to the app's *distribution* model (still ships inside the OS image, not a standalone store listing), just to what key stamps the CI-built artifact.

## Session 21 (2026-09-14) — reversed the bundled-model design, gated all monitoring on a real loaded model, unified network+file monitoring, and cleared a long-standing signing backlog

An architectural decision the user made explicit this session, not previously documented anywhere: **the on-device model is not going to be embedded in the app at all — it's dynamic, full stop.** This directly reverses session 20's `ModelUpdateManager` design, which deliberately bundled a placeholder model as a real APK asset (`63d9f9e`) specifically so `loadCurrentModelJson()` "always returns something usable from first launch, network or not." That reasoning is now explicitly overridden, not just quietly dropped — recorded here so a future session doesn't wonder why the bundled-asset design vanished.

1. **`ModelUpdateManager`: bundled fallback removed (commit `aa25bdf`).** `loadCurrentModelJson()` is now `String?` (was non-null `String` with an asset-read fallback) — returns `null` until a real download has succeeded at least once. New `hasLocalModel(): Boolean` and `suspend fun ensureModelLoaded(): Boolean` (returns `true` immediately if a model file already exists, otherwise forces an immediate manifest check regardless of the 24h staleness window — the existing `checkForUpdateIfStale()` is unchanged and still used for the coarse background poll). The bundled asset (`trigger-router/src/main/assets/on_device_network_model.json`) and its `knowledge-graph/noxos-app/comments/` archive entry are both deleted, not just unreferenced.
2. **Monitoring gated on a real model load, and unified to cover files too (commit `aa25bdf`).** Previously `FileArrivalWatcher.start()` ran unconditionally from `MainActivity.onCreate()` — every file dropped into Downloads was scanned regardless of whether network monitoring was even on. Now there is one lifecycle: tapping the (renamed) "Start Monitoring" button calls `ModelUpdateManager.ensureModelLoaded()` first; only on success does it proceed to the existing VPN-permission flow and start **both** `NetMonitor` and `FileArrivalWatcher` together. A failed load shows `"Couldn't load the threat model — check your connection and try again"` inline on `HomeScreen` and starts nothing. Stopping does the reverse — both watchers stop together. **Until monitoring is started, `FileArrivalWatcher` is simply never running, so every file is allowed through untouched by construction** — no new "allow" logic was needed, removing the unconditional `start()` call was the entire fix.
3. **UI text**: "Start Network Monitor"/"Stop Network Monitor" → "Start Monitoring"/"Stop Monitoring" (`HomeScreen.kt`), matching the widened scope. `HomeScreen`/`MainActivity`'s internal `netMonitorActive` state and `onToggleNetMonitor` callback were renamed to `monitoringActive`/`onToggleMonitoring` throughout, not just the button label.
4. **Real CI failure this exposed, root-caused, not worked around.** The first two fix attempts (cross-test file-state cleanup, then a defensive fake-HTTP-server rewrite) both still failed the same three tests on CI, always with a bare `java.lang.AssertionError` and no message — this codebase's test suites had never needed `testLogging.exceptionFormat` before, so Gradle's console only ever printed a file:line, never the actual assertion diff. Added `subprojects { tasks.withType<Test> { testLogging { exceptionFormat = FULL; showCauses = true; showStackTraces = true } } }` to the root `build.gradle.kts` (commit `d4474a7`) — a permanent addition, not a temporary diagnostic, since terse test-failure output had already cost two wasted fix attempts. With the real message visible (`expected:<Updated(newVersion=1)> but was:<Failed(reason=manifest unreachable)>`), the actual bug was obvious and CI-environment-specific theories (proxy env vars, IPv6/loopback quirks) turned out to be unnecessary: **`ModelUpdateManagerTest`'s `FakeHttpServer` called `client.getInputStream().bufferedReader().use { ... }` to read the request headers** — `.use {}` closes the reader on exit, and per `java.net.Socket`'s own contract, closing the stream returned by `getInputStream()` closes the *entire socket* — so the response was never written; the client's `HttpURLConnection` saw a closed connection before any response arrived, and both `httpGetText`/`httpGetBytes` swallow that as a generic `Exception` and return `null`. Fixed (commit `154a72f`) by reading the request without `.use{}`, deferring the actual close to the existing outer `finally { client.close() }`. This bug predates this session's edits — it was latent in the original `63d9f9e` test helper and just happened to only manifest in assertions that require a *genuinely successful* round trip, which is why it survived past session 20's original CI run.
5. **Verified live on Cuttlefish** (`cuttlefish_orchestrator`, device `127.0.0.1:6524`), not just CI-green: fresh debug APK from the now-passing run installed and launched; "Start Monitoring" button confirmed live; tapping it with `BuildConfig.MODEL_MANIFEST_URL` pointed at its still-unpublished S3 path produced exactly the expected `modelLoadError` text and left the app in `IDLE`; a file dropped into `/sdcard/Download` while idle was confirmed via `sqlite3` against the real on-device `audit_database` to have generated **zero** `quarantine_entries`/`audit_entries` rows and remained byte-for-byte on disk — monitoring genuinely never touches anything until a model is loaded.

## Session 19 (2026-09-13/14) — a real design bug from a peer review, a full comment-removal sweep, v2.0.1

1. **Real bug, found by a peer review session, fixed and CI-tested (commit `00da1ce`): the cheap-filter batch queue could starve permanently.** The review traced the exact gate in `NetMonitorService`'s capture loop (`if (verdict == null && ...)`) and found that once a destination is `FLAGGED`, `aclCache[dstIpStr]` is never `null` again — so a destination whose sample was lost (process restart, or a prior `NetworkSampleVmDispatcher` attempt that came back `Unknown`, which is *every* attempt right now given the `MANAGE_VIRTUAL_MACHINE` gap from session 18) can never re-enter the capture block, and never gets `cheapFilterChecked` set either. The "a retry will just repopulate the buffer" assumption from `discussions.md` item 3's original design doesn't hold in the shipped code. Worse: `nextCheapFilterBatch()`'s oldest-first, no-cutoff query means a stranded entry is *always* among the oldest unchecked rows, so it permanently occupies a batch slot — once 5+ (the batch size) accumulate, no new destination ever gets cheap-filter-checked again. Confirmed this exact failure mode had already happened in session 18's own testing (the `93.184.216.34` ICMP entry, `cheapFilterChecked=0` forever) without the systemic consequence being caught at the time.
   **Fix**: `RoomAclRepository.nextCheapFilterBatch()` now excludes entries older than a 5-minute staleness cutoff — the simpler of the two options the review proposed (vs. reworking the capture gate itself), and doesn't depend on retry timing at all. A stale, never-checked entry now permanently drops out of contention instead of permanently starving fresh ones — matches the originally-accepted "explicitly accept the loss" stance from `discussions.md` item 3, just actually implemented now. Two new tests (`RoomAclRepositoryTest`) cover both the basic exclusion and the actual regression shape (5 stranded entries + 1 fresh one, batch limit 5 — fresh one must still get through).
   **Everything else in that review came back clean**: the `CopyOnWriteArrayList` sample buffer (functionally fine vs. the originally-discussed mutex, one negligible unsynchronized race not worth fixing), `TcpRelayManager`'s per-read hashmap lookup (cheap, not worth avoiding), the proto-vocabulary fix, and all four session-18 quarantine fixes were all reviewed and found genuine and correct.

## Resolved — AVF compile blocker (early, carried from project start)

**Root cause, confirmed via `javap` against the real jar, not guessed:** `android.system.virtualmachine.*` (`VirtualMachine`, `VirtualMachineManager`, `VirtualMachineConfig`) are `@SystemApi`, absent from the public `compileSdk` jar. Google's own reference app (`MicrodroidDemoApp`, from `platform/packages/modules/Virtualization`) builds against them via Soong's `sdk_version: "system_current"`, which — inside a full AOSP tree — resolves to `prebuilts/sdk/<api>/system/android.jar`.

**Fix applied (no AOSP checkout needed):** `platform/prebuilts/sdk` is its own standalone AOSP git repo, independently cloneable. `trigger-router/build.gradle.kts` has a `fetchAvfSystemStub` Gradle task that downloads `35/system/android.jar` from `android.googlesource.com/platform/prebuilts/sdk` at build time (cached under `build/avf-stubs/`, not committed — it's a multi-MB AOSP binary) and wires it in as `compileOnly`. Verified locally via `javap` before writing any code that the jar actually contains `android/system/virtualmachine/*.class` with the expected method signatures.

**While verifying the method signatures, found the API shape had actually changed from what the code (and Google's `writeavfapp` doc, which reads as written for an older API level) assumed:**
- `VirtualMachineConfig.Builder` has **no `(Context, path)` constructor** in API 35 — only `Builder(Context)`. Fixed to build the config programmatically: `.setPayloadBinaryName("libnoxos_payload_stub.so")` + `.setProtectedVm(false)`.
- Builder method is `setProtectedVm(boolean)`, not `setProtected(boolean)`.
- `VirtualMachineManager` has no public constructor or `getInstance()` static — obtained via `context.getSystemService(VirtualMachineManager::class.java)`.
- `vm.connectVsock(long)` takes a `Long`; `VmPayloadProtocol.VSOCK_PORT` was an untyped `Int` literal (`5000`) — changed to `5000L`.

**Open question this surfaces, still not resolved:** if the host-side `VirtualMachineConfig` Builder no longer parses `assets/vm_config.json` directly (API 35 removed that constructor), it's unclear what role that JSON file still plays — whether Microdroid still reads it by convention on the guest side, or whether it's now fully redundant with `.setPayloadBinaryName()`/`.setApkPath()`. **Did not touch `app/src/main/assets/vm_config.json`** — needs verification against real Microdroid boot behavior (Phase 2), not a guess.

## Warden ACL + auto-scan (2026-09-10)

User's design ask, thought through before building (full rationale in `../PROJECT.md`'s "Threat analysis" section): turn the blocklist into a real ACL, flag new/unknown destinations for future AI analysis without paying per-packet cost, extend file scanning beyond the manual button to anything arriving via SD card/Bluetooth/Wi-Fi share, and make AI analysis opt-out-able. **App-side only this session** — no model, no EC2 inference yet, deliberately deferred. Landed as one commit (`21ed6c1`) via PR #1, merged to `main`.

**Real, working:**
- **3-state ACL** — `blocked_hosts`/`BlockedHostRepository` reworked into `acl_entries`/`AclEntity`/`AclRepository` (`ALLOWED`/`BLOCKED`/`FLAGGED`). `NetMonitorService` still drops `BLOCKED` flows exactly as before; a destination with no ACL entry at all now gets a one-time `FLAGGED` row written (`insertIfAbsent` — Room's `OnConflictStrategy.IGNORE`, so repeated packets from the same still-unresolved destination are free after the first) with reason "new destination, pending analysis" — this *is* the cost-gating mechanism the user asked for, not a queue or rate limiter bolted on separately. `FLAGGED` doesn't block traffic, it's a marker. The ACL screen (renamed "Access Control List") shows all three states with Allow/Block/Remove per row, so a flagged entry can be manually resolved today even with no model behind it yet.
- **Auto file-scan** — new `FileArrivalWatcher` (`trigger-router` module) registers a `ContentObserver` on `MediaStore.Downloads.EXTERNAL_CONTENT_URI` and auto-calls `TriggerRouter.scanFile()` on anything new, same code path as the manual "Select & Scan" button. One MediaStore collection, chosen because it's where SD-card-copy (via most file managers), Bluetooth OPP, and Wi-Fi-share apps all commonly land — not exhaustive of every possible storage location, a deliberate v1 scope cut. **Needed `MANAGE_EXTERNAL_STORAGE`** (All Files Access) — minSdk is 33, and there's no narrower runtime permission that lets one app see files another app wrote into Downloads; a real, sensitive, user-visible permission (system-settings toggle, not a normal runtime dialog), flagged as such rather than added quietly. Since Warden isn't Play-distributed, the usual app-review friction for this permission doesn't apply, but it's still worth remembering when this eventually becomes a priv-app (Phase 1c item 10 in [`../noxos-os/TASKS.md`](../noxos-os/TASKS.md)) — a priv-app could get equivalent access without the user-facing toggle at all.
- **AI opt-out** — new Settings toggle ("AI analysis of flagged traffic", default on, `WardenSettingsRepository.aiAnalysisEnabled`). Off means new destinations never get `FLAGGED` in the first place — no point tracking "pending analysis" for analysis that will never happen.

**Deliberately simplified, not faked:**
- File-arrival watching is Activity-scoped (starts/stops with `MainActivity`), not a persistent foreground service like `NetMonitorService` — won't catch files that arrive while the app isn't running. Same "honest about what's real" standard as everything else in this app; a real gap if unattended coverage matters, not fixed this session.

If a manual and an auto scan overlap, they share one `TriggerRouter.progress` `StateFlow`, which could show interleaved progress — not fixed, `TriggerRouter` has no concurrency guard and never did.

## Warden threat-analysis inference backend — the `noxos-app` side (2026-09-12, session 11)

Picking up the one thing session 10 explicitly deferred: `AclRepository.nextAnalysisBatch()` existed, was tested, and had zero callers — no model, no EC2 box, nothing to send a flagged entry to. See [`../noxos-inference/TASKS.md`](../noxos-inference/TASKS.md) for the new repo/model/infra side of this; this section is just the `noxos-app` code that calls it.

**`netmonitor/AnalysisDispatcher.kt` (new)**: polls `AclRepository.nextAnalysisBatch(10)` once a minute inside `NetMonitorService`'s existing `serviceScope` (a new `analysisDispatchJob`, started/cancelled alongside `aclJob`/`aiAnalysisSettingJob` — no new Service, no WorkManager dependency added, this reuses the coroutine loop pattern already in the file). For each flagged entry, POSTs to `<endpoint>/analyze/network` and writes `allow`/`block` back via the existing `AclRepository.allow()`/`.block()` — `uncertain` or any failure just leaves the entry `FLAGGED` for the next cycle, no new state introduced. Gated on both the existing `aiAnalysisEnabled` setting and a new `inferenceEndpointUrl` setting (empty = disabled).

**Real gap, flagged not hidden**: the POST body only carries what `AclEntry` actually has — `ip`, `priority`, `reason`, `first_flagged_epoch_millis`. The network classifier being built in `noxos-inference` is trained on richer per-flow features (port/protocol/volume/frequency) that Warden doesn't persist per-destination today — only sees transiently in `NetMonitorService`'s packet loop. Not resolved yet; documented in `noxos-inference/AGENTS.md` with the two real options (treat unknown-destination scoring as IP-reputation-style, or extend `AclEntity` — the Room schema already uses `fallbackToDestructiveMigration()`, so a version bump is cheap — once it's clear the model actually needs those columns). Don't build the schema extension speculatively before that's known.

**New settings, with real UI**: `WardenSettingsRepository` gained `inferenceEndpointUrl`/`inferenceApiKey` (DataStore-backed, both default empty). `SettingsScreen` gained a `SettingsTextEditRow` (dialog + `OutlinedTextField`, masked for the API key via `PasswordVisualTransformation`) under "Threat analysis" — the first editable-text setting in this app; every existing setting was a toggle/dropdown, so this is a new UI pattern, not just a new field.

**Real bug found and fixed while building this, unrelated to the dispatcher's own correctness**: `NetMonitorService`'s `VpnService.Builder` never called `addDisallowedApplication(packageName)`, so with `addRoute("0.0.0.0", 0)` the VPN tunnel would have captured Warden's *own* outgoing traffic too — meaning the dispatcher's HTTP calls to the inference box would have looped back into Warden's own tunnel instead of reaching the real network the moment network monitoring was active, the same failure class as backlog item 17's `TcpRelayManager` bug (session 10), just at the OS-routing level instead of the per-socket `protect()` level. Fixed with one call in `startMonitor()`, wrapped in try/catch for the declared `PackageManager.NameNotFoundException` (should never actually throw for the app's own package, but the API declares it checked). This fixes it for *any* future app-originated traffic, not just the dispatcher — deliberately chosen over calling `protect()` per-socket in `AnalysisDispatcher` itself, since `HttpURLConnection` doesn't expose its underlying socket to protect() before connecting, and per-socket protection is exactly the pattern that already caused one real bug in this codebase (session 10 item 5).

**Real test, not decorative**: `AnalysisDispatcherTest.kt` — `AnalysisDispatcher.requestVerdict()` was pulled into the companion object specifically so it needs no `WardenSettingsRepository` instance (which needs a real Android `Context`, unavailable in a plain-JUnit test without Robolectric) to test directly. Originally used JDK's `com.sun.net.httpserver.HttpServer` as a real local server — **replaced session 11 (commit `e6d7d52`) with a raw `ServerSocket`** after it turned out not to resolve in Android's Kotlin unit-test compile (see session 11 item 3 above) — same "real sockets, no mocking framework" style as `TcpRelayManagerTest`, asserting: a real `allow` verdict parses correctly, the API key is sent as a real `Authorization: Bearer` header, a non-200 response returns `null` instead of throwing, and an unreachable endpoint returns `null` instead of throwing. **Deliberately not using `org.json`**: Android's unit-test classpath stubs `org.json.*` the same way it stubs `android.*` (this module's `build.gradle.kts` already sets `unitTests.isReturnDefaultValues = true` for exactly this reason) — under that stub, `JSONObject` parsing would silently return defaults instead of real values, making the test pass or fail for the wrong reasons. Used hand-built/hand-parsed JSON instead (4 fixed fields out, one regex-extracted field in) — deliberately not a general JSON solution, fine because the request/response shapes are small and fixed; if the API shape grows, revisit with a real JSON library added as a `testImplementation`-only dependency for org.json (a documented, common Android workaround) rather than continuing to hand-roll parsing.

Instead hand-rolled a minimal split-relay in pure Kotlin, same shape as the existing UDP relay: new `TcpRelayManager` parses each TCP segment off the tun fd, keys a session table by the 4-tuple, and on SYN opens a real `protect()`'d `Socket` to the destination. Once connected it synthesizes a SYN-ACK back into the tun (the app's TCP stack has no idea it's talking to a relay), then a background coroutine pumps `Socket` input straight into synthesized data/FIN segments, while inbound data/FIN/RST packets get their payload written to the real socket and ACKed. Sequence/ack numbers are tracked per-session as unsigned 32-bit (`Long`, masked); `PacketUtils` gained `readUInt`/`writeUInt` and a real `buildTcpPacket` (pseudo-header checksum included). **Known, deliberate simplifications** (not bugs): no retransmission/window-scaling/reordering — relies on the real destination's own TCP for reliability and on the tun fd (a local kernel path, not a lossy network) rarely dropping; no TCP options echoed on our synthesized segments. Verified with a real JVM integration test (`TcpRelayManagerTest`, no Android/Robolectric needed) that drives a full SYN → data → reply → FIN cycle against a real loopback `ServerSocket` and asserts on the actual bytes relayed each direction — not a stub. **Confirmed on real hardware session 10.**

17. ~~**TCP relay: every real connect() times out on-device.**~~ — **root cause found and fixed 2026-09-10 (session 10).** The `protect()` return-value diagnostic from `d86774a` (pushed and merged this session) confirmed the leading hypothesis exactly: `protect()` was returning `false` for every TCP socket. Cause: `TcpRelayManager` called `protect()` on a bare `Socket()` before `connect()`/`bind()` — a plain `java.net.Socket` has no real underlying file descriptor until one of those is called, so there was nothing for `protect()` to act on, and the unprotected socket's SYN looped back into Warden's own tun interface instead of reaching the real network. Fixed with `session.socket.bind(InetSocketAddress(0))` right before `protect()`.
