# On-device network classifier — design history

Moved here from `discussions.md` (2026-09-16 knowledge-graph reorg) — this was the unfinalized design-review scratchpad for the network-side cheap-filter + on-device-classifier work, spanning `noxos-app` (dispatch/wire contract) and `noxos-inference` (model). Numbering below matches the original `discussions.md` item numbers for cross-reference.

## 1. Direction mismatch: the cheap filter may be inspecting the wrong side of the connection — RESOLVED session 17

pKVM isolation on network traffic was meant to close the same asymmetry the EXIF parser's fuzzing-found heap overflow demonstrated on the file side. But the packet sampled at "destination first flagged" time was the **outbound** packet — generated by this device's own OS, not attacker-controlled. The genuinely hostile bytes (a malicious server's response) are parsed later by `TcpRelayManager`'s reply-pump and never reached this mechanism as originally specified.

**Fixed, `noxos-app` commit `bcfda8e`**: the sample now includes the first **inbound** reply alongside the outbound packet. The guest-side check, once built, looks at destination-controlled bytes, not just the outbound one.

## 2. Session-scoped forgetting — RESOLVED, by design, not a bug

Session-scoping is the intended default tier, not a gap — the ACL is the permanence layer (local, persistent storage); a verdict a user wants to stick gets promoted there directly. Residual note: a destination nobody manually curates gets zero cross-session benefit from being resolved (re-flagged/re-checked every session) — a deliberate tradeoff, not something to "eventually improve."

## 3. In-memory packet buffer has no failure/recovery path — RESOLVED, with a real correction along the way

Original concern: `NetworkSampleVmDispatcher` needs `NetMonitorService.pendingPacketSamples` (RAM-only) to run its check; if the VPN process dies between flag and dispatch, the buffered packet is gone and the ACL row (`FLAGGED`, `cheapFilterChecked=false`) is silently stranded forever.

**Built, session 17 (`bcfda8e`)**: `pendingPacketSamples` became a per-destination `CopyOnWriteArrayList`, capped at 2 samples, that keeps appending until dispatched — a retried connection just adds to the buffer, no explicit staleness machinery needed.

**Correction, session 19, from peer review**: the "retry recovers it" premise was wrong. `NetMonitorService`'s capture loop only appends inside `if (verdict == null && ...)`, and once a destination is `FLAGGED`, `aclCache[dstIpStr]` is never `null` again — a retry never actually re-enters the append path. Worse, `nextCheapFilterBatch()`'s oldest-first-no-cutoff query meant a stranded entry permanently occupied a batch slot, starving destinations flagged after it.

**Real fix, session 19 (`00da1ce`)**: a 5-minute staleness cutoff on `nextCheapFilterBatch()` — simpler than fixing the capture gate, doesn't depend on retry timing. Not yet *visible* in the UI, just no longer *starving*. Lesson: verify the actual gate/call site a design depends on, not just that the data structure behaves correctly in isolation.

## 4. Wire contract locked ahead of the actual security semantics — acknowledged deliberate, spec still a draft

Locked early so `noxos-payload` wasn't blocked waiting on this repo. Still needs a real spec before the check is more than "technically real but zero security value" (e.g. "IP version is 4" — true of every packet that reaches the tun). Candidate starting spec (not decided): declared IP total-length vs. actual byte count; TCP SYN sanity (reserved bits, contradictory flags); UDP declared-length vs. actual size. Should be validated against item 1's inbound-vs-outbound finding first.

## 5 / 22.1 — On-device classifier: never wired into the live pipeline — tracked as backlog #19

See `TASKS.md` backlog item #19. Confirmed via grep (2026-09-16): `OnDeviceNetworkClassifier.kt` has zero call sites outside its own file and tests. The Safe/Flagged label users see is a plain `NetMonitorService` heuristic (relay failed OR ACL cache flagged), not the model. Matches `PROJECT.md`'s own "specced, not built" cascade-wiring note — a known gap, not a regression.

Earlier open question (2026-09-13, before the model was locked): with `noxos-app` only able to supply `dst_port`/`protocol` at the time, wiring the classifier in would have added asset/tree-walk/export-maintenance cost for a decision indistinguishable from the existing free `NetworkPriority.classify(port)` heuristic. Superseded once the 10-feature model was locked (item 11 below) — the feature-availability gap that motivated this caveat no longer applies, only the wiring-not-built gap does.

## 6. XGBoost `dump_model` → JSON transform: real edge-case risk — closed by model choice

XGBoost's dump format identifies a missing-value branch by child node ID (`missing: <id>`), not positionally — get the yes/no matching wrong and the interpreter silently gives the wrong answer specifically on the missing-value path (which was the dominant path when most features were defaulted). Once the 10-feature set was locked with real capture for every field (item 11), the missing-value path stopped being dominant, and `noxos-inference` kept XGBoost (not a switch to Random Forest) — the transform still needs a real parity test against the actual trained model's dump before shipping, not just the hand-written synthetic fixture in `OnDeviceNetworkClassifierTest`. Not yet done as of the last check.

## 7. VM-boot cost per newly-flagged destination vs. Pillar 1 — proposal: batching, not yet designed

Normal browsing can hit a dozen-plus genuinely-new destinations per page load; combined with item 2's per-session reset, a real burst of one-shot VM boots is possible at session start, in tension with the Lightweight pillar. Proposed fix (accepted tradeoff, not built): batch N destinations' samples into one VM invocation — first batch of a burst pays real lag, everything after resolves at full speed. Open: batch trigger (count vs. time window vs. whichever fires first), per-batch response shape, whether mixing destinations in one VM call changes the per-destination audit story. Not designed in detail.

## 8-9. On-device model choice and the real feature contract — RESOLVED 2026-09-14, see item 10-11 below

XGBoost vs. Random Forest was debated (a friend's concern that XGBoost needs 16-32+ boosting rounds to not underfit, and might be "too heavy for a phone" — the latter concern doesn't actually apply to this architecture, since the phone only ever walks an exported tree JSON, never runs XGBoost itself; phone-side cost is tree-count × depth regardless of training algorithm). Separately, a real contract bug was found and fixed: `noxos-app` originally sent field names/casing that didn't match any real training column at all (`protocol` vs `proto`, `"TCP"` vs `'tcp'`) — every real request was getting the same normal-defaulted prediction regardless of destination. Both concerns resolved by the feature-selection work below, which locked a real, verified contract.

## 10-11. On-device feature set — LOCKED 2026-09-14, build against this

**Final 10 fields**: `proto`, `dsport` (from `destPort`), `srcByteCount`, `srcPacketCount`, `dstByteCount`, `dstPacketCount`, `durationMillis`, `handshakeLatencyMillis`, plus derived `smean` (`srcByteCount/srcPacketCount`) and `dmean` (`dstByteCount/dstPacketCount`).

Resolved empirically against the fuller, real 2.28M-row UNSW-NB15 dataset (not the reduced 175K-row benchmark version, which was found to be artificially class-balanced): real `dsport` gave a genuine ~11% relative error-rate reduction over the original 7-field set; `smean`/`dmean` as derived ratios (no new capture) gave 0.9715→0.9724; `is_sm_ips_ports` gave nothing, dropped.

**Real unit-reconciliation, must not be skipped on any retrain**: `durationMillis`/`handshakeLatencyMillis` are milliseconds on the app side; the dataset's `dur`/`tcprtt` are seconds. Convert consistently.

**On-device compute estimate** (`n_estimators=200`, `max_depth=6`): ~1,200 threshold comparisons + 200 additions + one sigmoid per prediction, once per newly-flagged destination (not per-packet) — trivial for any modern phone CPU, expect low tens of µs to a fraction of a ms. Not benchmarked on a real device yet.

**F1 history, current source of truth is in `../noxos-inference/TASKS.md`'s "Train/test leakage fixed with StratifiedGroupKFold" section**: headline 0.9724 was real but inflated by row-level train/test leakage (54.68% of test rows had an exact duplicate feature-pattern in training); worst-case floor on genuinely novel patterns was F1≈0.88; the real, representative, leak-free number after switching to `StratifiedGroupKFold` is **F1≈0.9858** — that's the number to quote.

## 12. On-device vs. EC2 cascade — RESOLVED, see `PROJECT.md`

Not a primary/fallback choice — cheap filter → on-device classifier → EC2, escalating only the residue each stage doesn't resolve. Full diagram in `PROJECT.md`.

## 13. Server model (Tier 2) scope — decided 2026-09-14

Deliberately richer than the on-device model, not a hosted copy. Decided components: (1) persistent cross-session incident history as a feature only Tier 2 can hold (on-device ACL is deliberately session-scoped); (2) AbuseIPDB threat-intel — `blacklist` endpoint (5 pulls/day, cached daily, coarse first-pass) + `check` endpoint (1,000/day, live per-escalation lookup), with a static blocklist (FireHOL/Spamhaus) as fallback when AbuseIPDB is unreachable; (3) enrichment is a read-only lookup/cache, not something that "learns" — the *consuming model* retrains periodically, not the enrichment step; (4) training data's own synthetic `srcip`/`dstip` (UNSW-NB15's IXIA PerfectStorm lab addresses) explicitly rejected as a reputation source — no relationship to real internet addresses; (5) human-feedback batch retraining, periodic not online, with real safeguards specified (cap per-device influence per cycle, don't let a new label silently override a high-confidence prior without a second look, version/log every retrain); (6) SHAP explainability is server-side (Tier 2) only — too expensive to run on every Tier-1 call; on-device uses a cheaper rule-based substitute (see item 14).

## 14. Full XAI architecture — RESOLVED 2026-09-14, two pipelines that never touch at runtime

**Evaluation-phase (dev-facing, dataset-only, offline)** — PDP then ICE (targeted follow-up only on whatever PDP flags), run against the fixed public dataset, never against real Warden traffic, never on a phone, never automatic. PDP already run against the locked 10-feature model — flagged `smean` (bumpy) and `handshake_latency_millis` (suspiciously narrow 0-1.4ms range) as worth a closer look; ICE follow-up not yet run.

## 15. Proposed 3-tier network cascade + refined feedback/retraining loop — 2026-09-21, from a user ML-teaching session, NOT decided, not implemented

User-driven proposal, arrived at during a from-scratch ML teaching session, same spirit as the retrain ideas in `TASKS.md`'s Backlog (subsample/colsample_bytree, early-stopping ensemble sizing, teacher-student distillation — see that file, don't duplicate here). This item is architecture-level (where these models sit in the pipeline), not a training-config tweak, hence logged here instead.

**Proposed shape**:
1. **Tier 1 (on-device, cheapest): an autoencoder**, trained unsupervised on normal traffic only (no attack labels needed). Small tabular architecture (~10 features in, a bottleneck of a few dimensions, mirrored back out) — cheap enough to hand-roll a forward pass in Kotlin, same no-ML-runtime-dependency spirit as the existing tree interpreter (item 6). Job: flag traffic that doesn't resemble "normal," including genuinely novel attack shapes the supervised model was never trained on — something the tree model structurally cannot do no matter how much bigger it gets, since it only ever learned to recognize patterns present in its training labels.
2. **Tier 2 (on-device): the "student"** — the distilled tree ensemble from `TASKS.md`'s teacher-student idea, evaluated only on whatever Tier 1 flags. User floated possibly sizing the student "a bit deeper" than the original 100-150 tree plan — not sized yet, contingent on Tier 1 actually getting built first.
3. **Tier 3 (EC2): the "teacher"** — the CV-ensemble (k-fold averaged) model, for deepest verification of whatever clears tiers 1-2.

**Two real open questions, explicitly unresolved, need a real decision before this gets built — not assumed either way**:
- **Does Tier 1 run on *all* traffic, or only the existing sampled/cost-gated set?** Today's design only ever scores a destination once, via `AclRepository`'s cost gate (see `noxos-app`'s `nextCheapFilterBatch()`/ACL system, and item 12's cascade resolution). Running an anomaly check on literally all traffic is a materially different cost/coverage tradeoff than "flag once per destination, ever" — needs reconciling with the existing cost-gating design, not assumed compatible with it.
- **How does this interact with the existing pKVM cheap-filter stage** (the Microdroid VM header-sanity/protocol check, item 1's resolution, that currently feeds flagged traffic into the models)? User flagged directly: "the current check where anything that gets flagged in VMs is passed to models — we might need to change it." Whether the autoencoder sits before, after, or replaces part of that VM-based check is not decided.

**Feedback/retraining loop — refines item 13 point (5), same safeguards, more concrete mechanism**: cascade-confirmed verdicts (only when independent stages of the cascade agree with each other) accumulate as fresh, real, in-production labels. Periodic (never online/live) retraining of both the teacher and on-device models from this accumulated data, redeployed through the already-built OTA/GitHub Releases pipeline (`train-ondevice-model.yml`, `ondevice-model-latest`) — no new deploy infrastructure needed.

**Real safety concern, discussed directly, not hand-waved**: online/continuous learning on live traffic is a genuine data-poisoning attack surface — an adversary can slow-drip crafted "normal-looking" attack traffic to desensitize the model to it over time. Mitigations discussed: require multi-stage cascade agreement before accepting a new label as training-worthy (raises the bar for a poisoner — has to fool multiple independent stages at once, not one filter); cap per-device/per-source influence per retrain cycle (matches item 13 point 5's existing safeguard); human-reviewable, versioned retrains; never blind online updates. A dedicated "is this poisoning" classifier was considered and **explicitly deprioritized** in favor of these structural/cascade-based limits — poison-detection is itself an unsolved adversarial-research problem, not something to treat as solved by bolting on one more filter.

**Standing caveat that applies to any of this getting built, restated from `TASKS.md`'s Backlog**: user is explicitly skeptical the current on-device headline (F1 0.9858, post-`StratifiedGroupKFold` fix) is still too high and may be masking remaining overfitting. Not asking for that to be re-investigated right now — but it means any future model here (the autoencoder, a resized student, this whole cascade) needs validation against real, independently-verified ground truth before its own reported metrics are trusted, not an optional nice-to-have.

**Status: not decided, not implemented.** User wants to discuss and refine further before anything gets built — this is a design proposal on record, not a spec to build against yet (contrast with item 10-11's feature set, which explicitly is locked).

**Deployment-phase (user-facing, runtime)**: SHAP (server, Tier 2, exact per-instance `TreeExplainer`, affordable since Tier 2 only sees Tier 1's small residue) and BETA (on-device, Tier 1 — *"Black Box Explanations through Transparent Approximations"*, Lakkaraju/Bach/Leskovec, arXiv:1707.01154 — fit once offline at export time, runtime cost is just "which rule matched," as cheap as the tree walk itself). Replaces an earlier ad-hoc "furthest from typical value" placeholder. Open, undecided: whether to layer LIME's sparse local coefficients on top of BETA for more granularity — designed as a concept, not committed, decide once there's a concrete UI mockup. On-device UI (compact per-instance bar chart in `AuditDetailScreen`) not yet built — a rendering task, not new ML work.

RAM note: none of this costs meaningful on-device memory — only the tiny exported model/rule file ships to the phone, never the dataset or PDP/ICE sample.
